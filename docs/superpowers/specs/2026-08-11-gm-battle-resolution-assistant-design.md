# GM 战斗工序助手设计

## 目标

把战斗表定位为 GM 使用的手动结算助手：GM 在页面中选择/填写战斗双方角色，系统按规则工序整理技能和宝具，GM 决定生效、关闭或手动裁决，表格只自动计算明确数值。

## 产品边界

- QQ/行动统计只负责收集行动、统计回合资源，不参与完整战斗结算。
- 战斗表不从 QQ 自动导入技能/宝具发动队列。
- 战斗表可以和统计功能在魔力、状态、回合资源上联动。
- 战斗裁决最终由 GM 控制，系统只减少查顺序、查时机、算数值的重复劳动。

## 核心流程

1. GM 打开战斗表，选择当前战役和回合。
2. GM 给蓝方、黄方分别选择主力位和辅助位角色；两边都可从已保存角色卡选择。
3. 没有录入角色卡时，GM 可以临时手动输入名称和属性。
4. 系统读取参战角色的技能/宝具和技能模板。
5. 系统按发动时机分到：常驻、战斗开始时、初始工序、主要工序、最终工序、决胜结算。
6. GM 在每个工序里逐项选择：生效、关闭、需裁决。
7. 对明确数值效果，系统自动加入属性、胜率、保底、魔力消耗计算。
8. 对复杂效果，系统只展示原文和备注区，由 GM 手动填表。
9. 结算确认后，系统回写蓝方/双方必要资源；第一版优先保证魔力回写稳定。

## 数据设计

- 继续使用现有 `battle_sheet` JSON 字段保存战斗表状态，不新增数据库表。
- `bluePositions` 和 `yellowPositions` 都保存统一槽位结构：`position`、`mode`、`cardId`、`name`、`stats`。
- `mode = card` 表示从角色卡选择；`mode = manual` 表示 GM 临时手动输入。
- `skillQueue` 继续保存每个技能/宝具的工序、状态、生效等级、选择属性、GM 备注。
- `phaseState` 保存当前工序和每个工序是否确认。

## UI 设计

- 左侧：工序导航，显示每个工序是否确认、是否有待处理项。
- 中间：当前工序主操作区。
  - 编队页：蓝方/黄方都可选卡，也可手动输入。
  - 技能工序页：显示当前工序待处理技能/宝具。
  - 决胜页：显示最终胜率和结算确认。
- 右侧：技能影响预览和结算摘要。

## 第一版实现范围

- 修正蓝黄双方编队：两边都支持角色卡选择。
- 保留黄方手动输入作为 fallback。
- 让黄方选中角色的技能/宝具也进入工序队列。
- 保存/刷新恢复两边编队和技能队列。
- 保持现有魔力/胜率/结算确认流程可用。

## 不做的事

- 不让 QQ 自动驱动战斗结算。
- 不自动裁决复杂技能条件、反制、即死、石化等效果。
- 不新增后端表。
- 不改 Spring Boot 旧后端。
- 不一次性做完整状态系统自动联动。

## 验证标准

- 蓝方和黄方都能选择已保存角色卡。
- 黄方手动输入仍能用。
- 双方辅助位属性都按半值计入总属性。
- 双方技能/宝具都能按模板进入正确工序。
- 保存后刷新，双方编队和技能队列能恢复。
- 有未处理工序时，结算前会提醒 GM。
- `node` 纯函数测试和 `frontend npm run build` 通过。
