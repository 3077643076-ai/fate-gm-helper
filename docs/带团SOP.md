# 三国杯带团 SOP（dsh 执行版）v0.3 初稿

> 用途：dsh（AI）带三国杯时的标准作业流程。每一步写清五件事：
> **读什么 → 查什么 → 做什么 → 落到哪 → 回执什么**。
> 本文档是"流程主干"，配套工具（查卡/搜规则/记账/关卡）是流程的落地手段；
> 发送关卡是流程的监工，跳步或数字不符会被拦。
> 保密约定：本文档不含真实群号/QQ/昵称，敏感映射见本地配置表（不入 git）。
>
> v0.2 修订：按《三国杯结算记录-第1天.md》复盘补盲区——魔力口径表、结算前置
> 检查（口径冻结+需裁决清空）、行动可见性、结算后固定动作、公告去重。
> v0.3 修订：新增 3.4b 投点登记制——主从同投/乱投骰导致的判定归属误判

## 0. 角色与铁律（总则，永远生效）

**AI 的定位**：执行者和抄账人。规则裁决归 GM，状态记录归账本，出群安全归关卡。
AI 不"记住"任何游戏状态——所有状态以事实源（SQLite 库）为准，AI 只是读写它。

**三条铁律**（违反即事故）：
1. **状态只信库**：魔力/令咒/位置/灵脉归属，回答前必须先查库，禁止凭上下文记忆回答。
2. **引用必查证，数值信规则书**：提到任何技能/宝具/灵脉效果，必须附查证来源
   （判例/查卡/场上状态/规则库，见 3.2 查证路由）。角色卡只提供"有什么能力的名字"，
   魔力消耗/回转/具体效果一律以规则书/资源库为准（卡面可能版本不一致或填错，
   冲突时按规则书执行并登记差异提醒 GM）；查不到就标"需裁决"，
   禁止凭印象编效果。（教训：狂阶宝具功能被遗忘）
3. **出群必走关卡**：所有发往灵脉群/公屏的内容必须经过发送关卡校验；
   私组内容也统一走关卡（直通不校验），保证出口唯一、日志可查。

**术语**：
- 事实源：SQLite 库（战役/角色卡/状态/账本都在里面）
- 账本：魔力/资源变动流水表，每笔变动一行
- 别名注册表：俗称→标准名的映射，会自动生长（见第 4 节）
- 关卡：本地代理，伪装 NapCat 接口，写类消息按群分级校验
- 需裁决：AI 无法确定的事项清单，等 GM 拍板；拍板结果回写库/别名表

## 1. 开团前准备检查单

每次开团（或重启会话）后，按顺序核对，任何一项不满足先补再开：

1. 读当前战役、当前回合/时段（库：campaign、campaign_round）。
2. 读角色卡表，确认 7 组主从 14 张卡在库、无退场标记错误。
3. 读灵脉表，确认灵脉数量、归属与本团当前进度一致。
4. 读群映射配置表（本地文件）：私组 7、灵脉群、公屏、GM 群 → 群号 + 分级。
5. 读别名注册表当前版本号（每次新增别名版本 +1）。
6. 确认关卡服务在线（探活），NapCat 地址已切换到关卡端口。
7. 以上全部通过 → 向 GM 回执"就绪"（私组/GM 群），列出当前时段和待办行动数。

## 2. 时刻表与群体系（本项目实态）

**回合结构**：降临日 + 第 1~14 日，每日分[昼][夜]，共 29 个时段。
**行动提交约定**（GM 09-03 确认）：
- 玩家把行动写进**私组群公告** → 私组内发 `.确认行动` → 机器人回发确认公告。
- **公告是行动的可靠记录源**（私组聊天大量 RP 闲聊混流，不作为行动依据）。
- 行动截止时间由 GM 发在**公屏**（纯文字，如"明晚八点前提交第 N 日昼的行动"）。

**群分级与关卡策略**：

| 群类型 | 关卡策略 | 说明 |
|---|---|---|
| 私组（按职介命名，共 7） | 直通不校验 | 发错影响小；解析回执也发这里 |
| 灵脉群（群名=灵脉名+数值） | 严格校验 | 群名即灵脉状态情报，发错会污染局面 |
| 公屏（全员可见） | 严格校验 | 截止时间、全局播报，最不能出错 |
| GM 群 | 直通 | GM 私聊沟通、需裁决提醒走这里 |

**灵脉群名即状态**：GM 改灵脉群名维护"灵脉名 魔力量/人流量/战场宽度"，
任何灵脉状态变化后，SOP 第 3.6 步必须同步改群名。

## 3. 核心循环：每个时段的 SOP

### 3.1 时段开始（读状态）
- 读：库中当前回合/时段、上一时段的行动与结算结果、各角色当前魔力/令咒/状态/位置。
- 查：无（纯读库）。
- 做：生成"本时段开局简报"（各角色位置、魔力、上一时段未决事项）。
- 落：简报存档（交接表）。
- 回执：发 GM 群。禁止凭记忆开场——上一时段的所有数字以库为准。

### 3.2 玩家行动到达（解析五步）
触发：私组公告更新 或 `.确认行动` 指令。

1. **切分**：从公告取原文（`.确认行动` 时读回群公告并回发确认，原文为准）。
2. **实体识别**：逐词过别名注册表回退链（见第 4 节）——
   精确名 → 拼音 → 编辑距离 → 团内类型推理 → AI 语境猜测 → 都失败进需裁决。
3. **查证**（按问题类型路由，命中即附出处）：
   - **能力名字与归属**（这个单位有什么技能/宝具）→ 查**玩家角色卡**
     （查卡脚本输出技能名清单；卡是名字的来源）。
   - **能力的数值与效果**（魔力消耗/回转/具体效果文本）→ 一律以**规则书/资源库**
     为权威（搜规则脚本核对原文）——即使卡面写了不同数值也不采用。
     原因：玩家卡可能与规则版本不一致，或填写有误。
     卡面与规则书冲突 → 按规则书执行 + **登记差异条目**提醒 GM
     （填错还是版本差异，由 GM 定夺）。
   - **规则书查无的技能**（玩家自创）→ 卡面原文仅作参考，效果经 GM 确认后
     录入技能模板库（结构层，数值即从此有据），此后按模板执行。
   - **GM 特裁判例** → 覆盖以上一切（如"鲜血神殿解放不消耗行动"），先查判例。
   - **场上状态**（生效结界/buff/契约/灵脉归属，教训：张角回魔误判为自身技能，
     实为场上"阵地额魔池 90"）与**团配置**（灵脉规则/魔力口径表）→ 涉及即查。
   全部查不到 → 需裁决。查证输出保留出处，随行动记录一起落盘。
4. **落盘**：解析结果写库（行动表 + 涉及的魔力变动写账本，见 3.3）。
5. **回执**：私组回"我理解为：<角色><行动类别>→<目标>，魔力±<数>（事由）"。
   玩家纠正则以玩家为准，重解析、重新落盘，并把纠正写成别名（如适用）。

### 3.3 魔力变动记账（账本模式）
- 每一笔魔力变动**立即**调记账脚本入库：角色、回合、时段、±数、事由、来源（公告/判定/技能）。
- 数字必须来自原文或判定结果，AI 不得心算合并多笔。
- 当场可查：`结算` 脚本输出逐笔明细+当前余额，回执给玩家核对。
- **教训锚点**：第一天魔力结算丢失信息导致算错——根因是数字只存在于对话流中。
  自本 SOP 起，任何魔力数字不允许只存在于聊天记录，必须有一行账本。

### 3.3.1 魔力口径表（公式进库，禁止口算）
第一天复盘发现：比"丢信息"更常见的是"算错口径"（漏叠增源、漏技能加成、
超越回路未翻倍、魂食供魔多算/漏算、回魔来源误判）。因此：
- **所有公式结构化入库**（`mana_rules` 表或等价配置）：
  - 御主池上限 = 回路 + 增源/增殖的源（+50）
  - 从者池上限 = 150 + 技能加成（按卡登记）
  - 超越回路 = 每轮末 +X，若持 Own 工房灵脉则翻倍
  - 供魔口径 = 灵脉供魔 + 工房远程 + 阵地额魔池 + 魂食 + 回路补给（各自独立成行入账）
- 上限/补给计算一律由脚本按口径表执行，AI 只负责登记事实（谁的什么来源、数值多少），
  **不允许 AI 在对话里口算合计**。
- 口径有争议 → 不算，进需裁决；GM 定稿后**更新口径表**，然后重算该时段。

### 3.4 行动确认（.确认行动 流程）
1. 读本群当前公告原文（HTML 实体解码）。
2. 回发确认公告："已确认 <时间> + 公告原文"（原文回贴，不改写）。
3. 行动进库（状态=已确认）。

### 3.4b 投点登记制（判定单）

**问题锚点**：玩家会随手投骰（乱投无害但要防误结算）；主从两人各需投骰时，
AI 分不清"这个点数是谁、投给哪个判定"——09-04 广侦情报因此误发骑组，
侥幸结盟不撤回，否则就是信息泄露。

**流程**：
1. **先立单后投点**：行动解析完成后，每个待判定行动生成一张**判定单**并入库：
   编号、角色（主/从明确）、行动、判定类型、目标值、所属组、状态=待投。
   同组多张单时回执列清单："本时段待判定：①<从者>广泛侦查/50 ②<御主>情报调查/50"。
2. **投点必须挂单**：玩家 .ra 或口头报点后，AI 将结果匹配到具体判定单；
   同组多张单时**必须回执确认归属**（"35 → ①还是②？"），确认后才入账。
   禁止按出现顺序或猜测默认归属。
3. **无单不认**：没有对应判定单的骰子 = 无效投点（乱投/娱乐骰），
   不结算、不播报、不入账，私组提醒一句"该骰子无对应判定事项，已忽略"即止。
4. **结果定向**：判定结果只发给判定单上声明的组；情报类内容（广侦/情报调查）
   严禁跨组；再叠加 3.6 可见性规则（行动类型 × 场上状态）双重检查。
5. **补投与作废**：漏投的判定单保持"待投"并进结算前置检查（3.5 前置不通过不开结）；
   作废判定需 GM 确认，单据留痕不删除。
6. **取点与口径修正惯例（GM 口径，v0.3）**：
   - **取最早的确定投点**：一枚骰子成功挂单后即锁定，同一判定单的后续投点
     一律忽略（防刷骰）；重投必须 GM 同意，原点数留痕。
   - **目标值投错的宽免**：玩家可能忘了昼/夜补正按错误目标投骰
     （例：忘了昼补正投 ra30 的广泛侦查、或忘了在夜回合按昼目标投 ra60）。
     处理：出目按**正确口径**重判——重判通过 → 直接算过，
     回执注明实际口径（"忘昼补正投 30 出 20，按正确 50 判：过"），
     不要求重投；玩家说"就算这个得了"即此意。
     重判不过 → **默认从宽通过，但必须附带警告**（提醒该玩家下次按正确目标投），
     处理与警告一并记入判例留痕（GM 惯例口径，防惯例被反向利用刷判定）。

### 3.5 时段结算与对账（GM 触发：.推进）

**前置检查（不通过不开结）**——第一天教训：结算做到一半才发现有裁决问题，
导致"之前的结算全部回退"：
1. **需裁决清空**：本时段所有需裁决事项必须 GM 已拍板；有未决 → 列出并拒绝开结。
2. **口径冻结**：涉及供魔/上限/层数的方案，开结前向相关组回执一遍定稿口径
   （如"术组供魔=阵地90+超越回路40+灵脉50"），玩家无异议即冻结；
   开结后口径再变 → 视为新裁决，**本时段重开**（账本按时段重算，回滚零成本）。

**结算步骤**：
1. 汇总本时段全部已确认行动，未确认的列出并提醒 GM。
2. 按**结算链顺序**处理行动类别：机动 → 魂食 → 干涉 → 解放 → 制造 → 信息 → 休整 → 摧毁工房
   （顺序影响结果，如解放先于信息，神殿[永夜]不吃当晚补正——09-04 判例）。
3. 灵脉效果逐条查原文执行；判定掷骰按公告记录，成功率 ≥100% 自动成功。
4. **对账硬步骤**：结算脚本重算各角色魔力（账本 SUM + 口径表公式），与库中角色状态比对——
   不一致 → 停止播报，输出差异清单给 GM，人工裁决后修正账本。
5. 结算结果落盘（状态库+账本），生成时段摘要。
6. 回执：GM 群先发结算摘要，GM 确认后再执行 3.6 播报。

### 3.6 播报（分级出口 + 可见性规则）

**可见性先行**——可见性不是行动类型的固有属性，而是"行动类型 × 场上状态"共同决定。
（09-06 事故根因：魂食默认结算结束后发公屏播报，没有问题；但当目标灵脉存在
[魔术结界：鲜血神殿]时，其效果"隐藏当前灵脉上[遮蔽魂食]成功的信息"——
播报时忽略了场上宝具，才发了不该发的）：
- 播报前必须查证场上状态：目标灵脉/相关单位当前生效的宝具、结界、技能里
  有无"隐藏/遮蔽信息"类效果（查库中场上状态 + 搜规则核对原文，禁止凭记忆判断）。
- 有隐藏效果 → 相关信息只在相关私组回执，禁止发灵脉群/公屏。
- 无隐藏效果 → 按默认规则播报（如魂食结算后发公屏）。
- 灵脉群/公屏**禁止出现职阶与主从配对**，一律用代号（私组可说）。

**分级出口**：
- 私组：各自组内回执本组结算结果（直通）。
- 灵脉群：本灵脉变化（归属/状态/群名所需数值）——严格校验后发送。
- 公屏：GM 明确要求的全局播报才发——严格校验后发送。公屏原则仅 GM 发。
- **灵脉状态变化 → 同步 .改群名**（群名=灵脉名+魔力量/人流量/战场宽度）。
- **公告去重**：每群每类公告只保留最新一条，重发前撤旧（09-06 教训：状态记录公告重复）。

### 3.7 结算后固定动作（清单化，逐项打勾）
第一天复盘发现"结算完≠收尾完"，以下每项必须逐组核对：
1. 名片/群名刷新检查：各角色魔力名片已更新；灵脉群名已同步（09-06 有 6 组名片漏刷）。
2. 溢出魔力提醒：满池组列出，提示转魔（.转魔 台账）。
3. 状态效果清理：乐不思蜀等带持续/清空条件的 buff 按规则原文处理。
4. 需裁决队列：本时段新增裁决全部关闭；未决转下一时段并标注。
5. 判例沉淀：本时段 GM 特裁写进判例记录。

## 4. 指代与别名处理（回退链 + 生长机制）

**解析一个词的顺序**：
1. 精确匹配（角色代号/灵脉名/技能宝具全名）
2. 别名注册表（俗称→标准名）
3. 拼音容错（同音字：魔镜→魔境的智慧）
4. 编辑距离容错（小错字）
5. **团内类型推理**（泛用指代）：词是通用概念（神殿/教会/据点）→
   查团实体中该类型的对象——唯一→解析为它；多个→回执列候选；零个→用通用解释并回执确认。
6. AI 语境猜测（附猜测理由）→ GM/玩家确认后入库
7. 全部失败 → 需裁决

**唯一性复查**：别名解析的每次落地都核对目标实体当前是否唯一；
局面变化导致不再唯一 → 自动降级为回执确认，防止旧简称漂移。

**别名的四种来源**：
- 预置（职介通用外号：咖喱棒=弓 等，首批已整理待 GM 过目）
- 自动（拼音/编辑距离命中，无需维护）
- 教学式（拦截/回执纠正时，GM 或玩家确认一条 → 入库一条，版本+1）
- 挖掘式（定期扫群聊 jsonl 高频未识别词，批量生成候选给 GM 勾选）

**已知黑话首版**（源自《术语别名映射.md》09-04 首建版，随团聊追加）：
- 魔镜/魔镜卢恩魔术/魔境 = 魔境的智慧 → 获取卢恩符文（效果2）（杀从·贾诩；谐音镜/境）
- 空花/搓空花 = 虚荣的空中庭院（解放方式1）（术御·曹植）
- 乐不思蜀 = 洛阳[奏乐]的层数名称 → 代指奏乐行动（弓御）；奏乐也泛指该行动
- 广侦/广域/广域侦查 = 广泛侦查（昼 +20%）；情报调查 = 御主行动

## 5. 需裁决处理

**进队列的条件**：规则原文含糊/冲突、别名全链失败、行动意图二义、数值对不上账。
**流程**：写库（编号、上下文、AI 猜测与理由）→ GM 群提醒 → GM 拍板（.裁决 <编号> <内容>）
→ 执行裁决结果 → 能沉淀的沉淀（别名/判例/规则补丁），状态变更落账本。
**纪律**：需裁决未决时，相关行动保持"待定"，不猜测执行、不播报。

## 6. 异常与兜底

| 情形 | 处理 |
|---|---|
| 玩家私聊/闲聊里说了行动 | 不作为行动，引导写公告（公告才是行动源） |
| 公告读不到/为空 | 回执"未读到公告"，让玩家重写；禁止凭聊天记忆补行动 |
| 机器人掉线期间的消息 | 公告长期保存可补读；纯聊天缺失就标注"该时段信息不全"交 GM |
| 玩家书面纠正 AI 理解 | 以纠正为准重落盘；可沉淀的写别名 |
| 库数据与群名/公告矛盾 | 停止自动处理，报 GM 裁决 |
| 关卡拦截 | 按拦截说明改写或进需裁决；拦截记录留痕供 GM 事后查看 |
