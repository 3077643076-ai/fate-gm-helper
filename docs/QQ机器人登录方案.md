# QQ 机器人登录方案（思路集）

> 2026-09-16 起稿。目标：回答"怎么把 QQ 登录这件事**做稳**"，尤其是**换机器/分发给别人之后不出问题**。
> 现状可用但脆：机器人能跑，可是一旦迁移或分发给别人就会遇到各种环境问题。
> 本文只谈方案与取舍，不涉及今晚动手（用户定：先出思路，之后再实现）。

## 一、要解决的是什么

工作台需要 QQ 连接来做四件事：**读群公告、AI 代收行动、催交、发公告**（`.从者行动` 等群指令也是走这条链路）。
难的不是代码，是"**让一个第三方 QQ 协议端在某台机器上稳定登着**"。

### 0. 用户实际痛点（2026-09-16 夜补充，优先级高于下面的选型）

用户原话："每次都会弹出 napcat 的终端，我关了它好像也连得上；但是修改这个系统的时候它要重启，
我没什么好办法；海豹那个就网页扫码、保存账号，多方便。"

**这三件事与"换不换协议端"无关，都是现有架构内的进程管理问题：**

| 痛点 | 成因（对着代码确认） | 修法 |
| --- | --- | --- |
| 每次弹终端窗口 | 我们用 `cmd.exe /c launcher-user.bat` 拉起，bat 末尾有 `pause` → 控制台一直挂着（关掉它不影响机器人，因为 NapCat 已注入进 QQ） | 不走 bat：直接 `NapCatWinBootMain.exe <QQ路径> <Hook.dll> <QQ号>`（参数已从 launch.log 实测确认），并自行写 `loadNapCat.js`（bat 里只有一句 import）；输出写日志文件，`windowsHide` + 不产生控制台 → 永不弹窗 |
| 改工作台要重启机器人 | NapCat 是后端进程的**子进程**，重启后端/关 exe 时被进程树一起杀（今晚误杀两次就是这么来的） | `detached + hidden` 放飞成独立进程，PID 写 `data/napcat/napcat.pid`；工作台只连它的 OneBot WS。UI 给 `启动/停止/重启机器人` 三个按钮，停止时按 PID 精确停 |
| 想要"网页扫码 + 记住账号" | **其实已有**：二维码读 `cache/qrcode.png` 在网页显示；登录态存在 `data/napcat/config/`，下次用 `-q <QQ>` 快速登录 | 补一个账号面板：`已登录 <QQ>（<昵称>）` / `未登录` + `退出登录（换账号）`；并保证登录态跟着数据目录走（迁移/备份一并覆盖） |

> 结论：**先做这三件（约 40 分钟），NapCat 立刻就不"麻烦"了**；将来若真的换成 Milky，
> 也只是替换底层协议端，这套"进程管理 + 账号面板"的设计照样复用。

### 实测证据（2026-09-16，都在本机验证过）

| 事实 | 证据 |
| --- | --- |
| `NapCat.Shell` 是**注入本机 QQ 客户端**的 | `launcher-user.bat` 实质是 `NapCatWinBootMain.exe <QQ.exe> <Hook.dll> <QQ号>`；启动后本机 QQ 被机器人占用 |
| 因此**一个 QQ 客户端只能登一个号** | 机器人号与 GM 自己的号在同一台机器上互斥（这正是本需求起点） |
| 海豹核心能并存的原因 | 它 v1.5.1 起"内置客户端"直接拉起自带的 `Lagrange.Milky` / `Yogurt`（独立进程，不碰本机 QQ 客户端） |
| GitHub Release 资产在本机网络**假通** | `api.github.com` 通、`releases/latest/download/...zip` 返回 200 + content-length，但重定向到 `release-assets.githubusercontent.com` 后 body 不下载（18 秒 < 5MB） |
| NapCat 各包体积（v4.18.28） | `NapCat.Shell.zip` 28.1MB（注入版）；`NapCat.Framework.zip` 28.9MB；`NapCat.Shell.Windows.OneKey.zip` **1.0MB（安装器，自己去装一份 QQ）**；`NapCat.Shell.Windows.Node.zip` 111.3MB |
| NapCat 必须有 QQ | 官方安装文档第一条就是"安装对应版本的 NTQQ"，OneKey 只是"代为安装" |
| 海豹的 Milky 方案也有门槛 | Yogurt / Lagrange.Milky 分离部署要**自行申请 Signer Token**；海豹手册本身也提示第三方协议随时可能失效、有封号风险 |

### 登录态到底包含什么（迁移要带的东西）

| 位置 | 内容 | 体积（本机实测） | 迁移时必须带？ |
| --- | --- | --- | --- |
| `<data>/napcat/` | NapCat 本体 + `config/`（账号配置、WebUI token、onebot token）+ `guild1.db` + `cache/` | 122.6MB | ✅ 带了就不用重新扫码 |
| `%APPDATA%\Tencent\QQ` | QQ 客户端自身的数据/会话 | 230MB | ✅ 少了他就快速登录不了，要重扫 |
| `%APPDATA%\QQ` | 另一处 QQ 数据（版本差异） | 527MB | ⚠️ 待确认 |
| `C:\Program Files\Tencent\QQNT` | QQ 本体（机器人注入的目标） | **1172MB** | ❌ 新机器重装更新 |
| `Documents\Tencent Files` | 聊天记录/文件 | 6.4GB | ❌ 与登录无关 |

**结论（迁移专项）**：现在 U 盘一键备份只备份了数据库/角色卡/台账/AI记忆/历史存档 ——
**没备份任何登录态**，所以"搬家后要重装 QQ + 重新扫码"是必然的。要么补进备份，要么在文档里把预期写清楚。

## 二、设计的硬约束

1. **迁移友好**：换机器/换系统后，尽量只做"插U盘 + 拷贝数据"，而不是重新装一套 QQ 环境。
2. **分发给别人**：拿到发行包的人未必装过 QQ；且他们的网络同样下不动 GitHub Release 资产。
3. **想和自己的 QQ 并存**（本轮需求）：机器人号在线时，GM 自己的号也能开。
4. **非商业**：NapCat 许可只允许非商业随包分发（已按许可附原文与来源声明）。
5. **不想折腾**：出错时要能一眼看出卡在哪一步（现在这一点已经补得差不多）。
6. **网络受限**：任何"自动下载"都必须有镜像/离线兜底。

## 三、思路（按"改动量 / 风险"分组）

### 思路 A：把"QQ 从哪来"做成三种模式（配置化）——**是其它一切方案的地基**

把协议端抽象成三个互斥模式，业务代码只认一个 OneBot 11 入口：

| 模式 | 协议端在哪 | 适合谁 | 我们的改动 |
| --- | --- | --- | --- |
| `local-inject` | 本机 QQ 注入（现有 NapCat.Shell） | 单人自用、能接受退自己 QQ | 已完成 |
| `standalone` | 本机独立 QQ 环境（思路 C） | 想和本机 QQ 并存 | 启动器指向独立 QQ 目录 |
| `remote` | 另一台机器（思路 D） | 多机/分发/长期常开 | 只需 `wsUrl` 指远端 + 连接测试 |

**落地要点**：`onebot_bot_config` 加 `mode` 字段；"机器人连接"页用三选一 + 每模式的引导文案与状态显示；
后端启动器按 mode 分派。**好处：任何方案变化都不动业务代码**（这是本项目的核心不变量）。

### 思路 B：安装/下载做成"多源 + 离线兜底"（已大部分落地）

- 顺序：**本机已有 → 随包内置 → 直连 → 镜像（ghproxy/gh-proxy/ghfast）→ 手动指定目录**
- 加"可达性探测"再选源：先 HEAD/小范围 GET 试各源，谁能在 N 秒内出数据就用谁（避免"200 但不动"）
- **离线包优先**：发行 zip 已经内置 NapCat（122MB）；对外分发时引导"用网盘/QQ 群里传包"，别指望他们下 GitHub
- 失败必须可见：现在已有 30 秒卡住检测 + `launch.log` + 页面显示 `flowError`

### 思路 C：给机器人**一份独立的 QQ 环境**（=海豹那种"并存"效果，但仍走 OneBot）

三条实现路径，按省事程度：

| 子方案 | 做法 | 优点 | 代价/风险 |
| --- | --- | --- | --- |
| **C1 复制本机 QQNT** | 把 `C:\Program Files\Tencent\QQNT`（1172MB）复制一份到别处，启动器直接 `NapCatWinBootMain.exe <副本>\QQ.exe <hook> <QQ>`（绕开 bat 的注册表探测） | **零下载**、10 分钟可试出结论 | 不知 QQNT 是否允许多开（可能有单实例互斥）；副本占 1.2GB |
| **C2 NapCat OneKey** | 下载 1MB 的 OneKey 包 → 跑它的安装器（自己从腾讯 CDN 装一份独立 QQ） | 官方路线；QQ 从 `dldir1.qq.com` 下（国内快） | 安装器行为未知（是否可无人值守）；多下载约 200MB |
| **C3 真·海豹同款（Milky）** | 接 `Yogurt` / `Lagrange.Milky` 协议端 | 最彻底：不依赖任何 QQ 客户端 | 我们要写 **Milky 协议适配层**（现在只有 OneBot 11）；用户要自行申请 **Signer Token**；协议随时变 |

> 建议先花 10 分钟试 **C1**：能成就基本等于拿到海豹的效果，且代码改动最小（只多一个"独立 QQ 目录"配置）。
> C1 失败再考虑 C2；C3 留到最后，除非将来要"零依赖分发给别人"。

### 思路 D：把机器人放到**另一台常开的机器**（零代码，最稳）

- 旧笔记本 / 迷你主机 / 家里那台常开的机器（或 WSL）跑协议端，工作台只填 `wsUrl=http://那台:3001`
- 好处：① 自己的 QQ 与本机完全无关 ② 工作台迁移零成本（登录态跟着那台机器走）③ 分发给别人时只给工作台
- 代价：需要那台机器常开；要保证那台的 3001 端口对局域网开放（防火墙放行）
- 我们能做的：连接测试按钮 + 远端地址的健康检查提示（小改动）

### 思路 E：不依赖 QQ 的**降级路径**（保底，已具备基础）

- 群公告可以**手动粘贴**进页面 → 走同一套解析/登记（解析器已经很强：59 条噪音清零、真实公告 7/7 全解析）
- 意义：QQ 侧无论怎么崩，GM 的结算流程不中断；QQ 只是"自动化输入源"
- 可以补一个"粘贴公告并登记"的入口（成本很低，价值很高）

### 思路 F：登录态可移植（迁移专项）

- 明确清单（见上表）：`<data>/napcat/` + `%APPDATA%\Tencent\QQ`（+ 待确认 `%APPDATA%\QQ`）
- **把这两处加进 `一键备份到U盘.bat`**，并在 `说明_先读我.md` 写清"拷回去就能继续用，不用重新扫码"
- 注意：这些目录含 QQ 会话凭据，属敏感数据 → 只能放本地/U 盘，不能进仓库、不能随发行包分发

## 四、建议的实施顺序（每步都能独立交付）

1. **思路 A + E**（地基 + 保底）：模式配置化 + 手动粘贴公告入口。改动小，立刻让"QQ 不可用"不再是卡点。
2. **思路 B 收尾**：多源探测 + 失败可视化（大部分已做，补"先探测再选源"）。
3. **思路 F**：登录态纳入 U 盘备份 + 迁移文档写清。 → 直接解决"迁移后会遇到各种问题"。
4. **思路 D**：远端模式引导 + 连接测试。
5. **思路 C1 实测**（10 分钟）：QQNT 能否多开；成功则做 `standalone` 模式；失败再谈 C2。
6. **思路 C3（Milky）**：只在"要零依赖分发给别人"成为硬需求时才做（要评估 Signer Token 门槛）。

## 五、待实测确认的开放问题

- [ ] **C1 关键前提**：同一台机器上，QQNT 能否同时跑两个实例（两个账号）？→ 决定"复制 QQNT"这条路成不成立
- [ ] **C2 前提**：NapCat OneKey 的安装器能否无人值守（命令行）跑完？装出来的 QQ 用的是独立数据目录吗？
- [ ] `%APPDATA%\QQ`（527MB）到底是什么、是否属于登录态
- [ ] 海豹内置客户端的实测结论（用户自测）：自己的 QQ 在线时机器人能否同时在线、是否需要 Signer Token
- [ ] 迁移后"不用重新扫码"是否真能成立（把 napcat/ + QQ 数据目录一起带走试一次）

## 六、不变量（无论走哪条路都不要破坏）

1. 业务代码**只认一个 OneBot 11 入口**；协议端永远可替换（换协议端不写业务代码）。
2. 登录态与配置一律放**数据目录**（`FATE_DATA_DIR`），不放程序目录 —— 保证便携 exe 解包到临时目录也能长期保存。
3. 任何自动下载都必须有**镜像与离线兜底**，且失败要能指出具体卡在哪一步。
